# agenthub MVP：本地发现、战队推荐与执行闭环

设计笔记，2026-10-11。此文包含调研结论和后续设想；已发布能力以根目录 README 为准。首版采用本地服务与网页工作台，优先完成 Kimi 的拆解、确认、顺序执行、review 与反馈闭环。

## 产品判断

第一版做“本地服务 + Web 界面”，保留以后封装 Mac 客户端的边界。启动命令可以是 `agenthub start`，打开本地界面；提供状态和停止命令。浏览器关闭后，任务继续由本地服务管理。网页负责配置与交互，进程发现、额度查询、CLI 执行和持久化全部在本地服务。

网页按桌面工作台设计：全高布局，左侧项目／任务历史，中间对话与结果，右侧可折叠的分工、执行者状态和产物详情。首次配置引导与全局设置使用同一套配置组件。第一版不制作 Mac 安装包；界面组件与服务通信分离，方便未来直接复用到 Mac 客户端。

第一版的价值是：识别用户已有的工具和资源，解释如何配置 leader／执行者，再让一个真实任务走完拆解、实现、review 和汇总。Mac 窗口、菜单栏、系统通知与应用更新可以后加；它们不应决定最初的执行架构。

## 全局配置流程：首次安装引导与后续修改

这是产品级配置，跨项目和任务复用。首次启动通过引导完成；使用过程中可在设置中重新发现工具、同步模型和额度、更新资料、重新推荐或手动修改战队。每次保存生成配置版本，任务引用具体版本。

1. **发现与选择工具**：第一阶段仅实现 Kimi 的安装、版本和登录检测状态及手动路径；后续扩展五种目标形态。Aiden 原生和 Aiden × Codex 分开，保留真实启动环境。检测到不代表自动纳入战队。
2. **同步资源**：对用户选择的工具获取账号可见模型、thinking 档位、额度窗口与重置时间。模型列表支持搜索；探测失败提供默认模型／手动录入，标记未验证。
3. **补充能力资料**：按规范化模型身份查询官方资料、可追溯的编码／工具调用评测，保留来源与更新时间；区分模型测试和 agent + 模型组合表现。未识别的网关别名不要自动等同公开模型。
4. **推荐战队**：推荐“均衡／节省额度／优先质量”三套方案；每套展示 leader、编码、review 的模型与 thinking，以及理由、共享额度情况和缺失数据。用户可修改、锁定某个角色并重新推荐。
5. **保存全局战队**：确定一个 leader 和多个执行者 profile，保存模型、thinking、职责描述及推荐依据。此后创建任务直接使用已保存的战队。引导完成后可以进入工作台试运行一个任务。

模型资料是相对慢变化的数据；额度、登录和限流是快速变化的数据。资料更新失败可保留缓存，额度刷新失败则显示“最后查询时间／已过期／未知”。不能把查询失败显示成零额度，也不能把历史百分比称为实时值。

## 推荐机制

推荐对象是 `CLI/runtime + provider/account + model + thinking` 的执行组合。需要至少三层独立身份：

- **Runtime**：工具、版本、执行路径／wrapper 与环境。
- **Account／QuotaPool**：真实账号、订阅和共享额度窗口。
- **Profile**：leader 或某个“苦力强”，引用 runtime／账号，配置模型、thinking 和职责描述。

多个 profile 可以指向同一个 runtime、同一个模型，但同一账号的共享额度只能算一份。额度单位可能是窗口占用百分比、请求数、credits 或 API 余额；它们也不等于还剩多少上下文 token。

第一版建议由明确规则筛选可运行组合，再按任务适配度、额度可用性、速度与用户偏好排序。网上资料用于补证据；LLM 用于解释推荐，不独自决定兼容性和额度数值。推荐不必等 leader 已经选定，避免“先选 leader 才能推荐 leader”的循环。

推荐理由应该具体，例如：“该组合适合复杂拆解；保留短窗口额度给 leader；实现交给另一个额度池充足的组合；review 使用不同组合提供额外检查”。数据不足时输出条件式建议和置信度，不生成貌似精确的统一能力分数。用户可把“这个模型在我的项目中表现好／不好”作为本地偏好覆盖。

配置阶段保存的是全局战队及选择策略。单次任务里的 leader 从这份战队中选择执行者并分配工作，不重复安装引导或全局战队推荐，也不因额度刷新自动改写全局配置。额度不足时可在任务分工方案中建议使用已配置的其他执行者，随方案一起由用户确认。

## 单次任务流程：拆解、确认、执行

1. 用户选择项目并提交需求，系统记录当前全局战队配置版本。
2. 已配置的 leader 分析需求，从战队中选择执行者，给出任务拆解、依赖顺序、验收条件和分工方案。
3. 用户确认或调整分工；确认前可以继续与 leader 讨论，编码子任务尚未派发。
4. 按确认方案执行，展示进度；需要补信息或改变已确认方案时，让用户介入。
5. 按方案进行 review／有限返工，leader 汇总结果与产物。
6. 用户可对交付结果继续反馈。反馈留在同一任务中，开启新一轮：leader 分析需要调整的部分、给出新分工，用户确认后执行，再 review 和汇总。保留每轮方案、执行日志、结果与反馈。

任务使用配置快照。后续全局设置修改默认应用于新任务；已有任务继续使用原版本，避免模型、thinking 或执行者在运行中悄悄变化。leader 的分析本身会调用模型；“确认后执行”指确认后才派发实施子任务。

“最多一次返工”限制的是每轮实施／review 中的自动修正次数，不限制用户反馈次数。达到自动返工上限时，leader 交付当前结果和未解决事项，用户仍可继续反馈。仅讨论或解释的问题无需启动编码子任务。

## 执行权限：参考 botmux 的实际机制

已核对 [Kimi adapter](https://github.com/deepcoldy/botmux/blob/ff803e6bc3c81fe700799cdf8cf2d1819965016b/src/adapters/cli/kimi.ts#L21) 和 [沙盒配置](https://github.com/deepcoldy/botmux/blob/ff803e6bc3c81fe700799cdf8cf2d1819965016b/src/bot-registry.ts#L1669)：

- botmux 默认给 Kimi 加 `--yolo`；`disableCliBypass: true` 时不加该参数。
- 本机 Kimi 为 `2.1.1`，本次执行 `kimi --help` 显示：`--yolo` 是 Ask When Needed，普通编辑和命令自动执行，风险操作、提问和计划仍会询问。`--auto` 是 Never Ask，第一版不将它设为默认。
- agenthub 第一版复用这个启动策略，并在工作台承接 Kimi 的原生询问／审批。任务分工确认是 agenthub 层的执行入口；CLI 运行期间仍可以要求用户回答问题或批准操作。
- botmux 文件沙盒是独立可选机制，缺省配置为 off。工作目录本身不是文件访问隔离。第一版按其默认本地执行方式验证；可选沙盒不能在未实际实现和验证时宣称已经提供。
- 保留关闭自动执行参数的设置。Kimi 当前版本的参数与语义应以本机探测为准，不能沿用旧版文档把 `--yolo` 描述为全程免询问。

本机帮助还提供 `acp`（stdio）和 prompt 模式的 `stream-json`，可作为结构化结果与询问的接入候选。具体使用哪一条路径由实现阶段的协议验证决定。

## MVP 范围与界面

四个界面足够：**工具与账号 → 战队配置 → 任务工作台 → 结果与历史**。模型资料和额度详情可以作为侧栏，第一版无需独立模型评测中心。

MVP 应包含：本地探测、模型同步和降级、可查询账号的额度快照、可编辑战队推荐、统一任务入口、分工确认、实现与 review、取消、日志和持久化。建议并发先有小上限，返工次数有边界；编码任务先按项目串行，review 读同一份产物。后续需要并发改代码时再增加 worktree 分支隔离和合并。

按已确认顺序实现：**先用 Kimi 跑完整真实闭环，再接入其他 coding agent。** 第一阶段的发现、模型／thinking、额度、全局配置和任务执行都围绕 Kimi 展开；保留可扩展的适配器接口，其余工具的实现排在 Kimi 闭环验收之后。

第一阶段验收路径：

1. 发现本机 Kimi，核对实际版本、登录状态、模型列表、thinking 支持及额度查询能力；拿不到的数据明确显示状态。
2. 保存全局 Kimi 战队：leader、编码执行者、reviewer 使用独立 profile 和会话；可使用相同模型，模型／thinking 是否可选取决于真实探测。同一账号的额度仍共享。
3. 用户在一个真实项目提交需求，Kimi leader 输出任务拆解、分工和验收条件。
4. 用户确认后，编码执行者完成实际文件修改，reviewer 检查产物与验证结果，leader 汇总交付。
5. 验证进度、最终结果采集、取消和持久化；明确中断／重启后的恢复行为。若 botmux 现有 Kimi 桥不能满足最终结果与会话识别要求，先补齐或实现 Kimi 原生桥接，不以终端静默判定任务成功。
6. 用户在首次交付后提出一个具体调整，验证同任务新一轮的拆解、确认、修改、review、汇总和历史保留。

这轮使用真实 Kimi 调用及项目产物验证，不用模拟回复替代闭环。其余 agent 的接入顺序待 Kimi 闭环后再确定。

首个验收项目使用独立的小型任务清单应用：添加／完成／删除任务、按完成状态筛选、刷新后保留数据，并用测试验证核心行为。首次交付后追加“任务优先级及筛选”的用户反馈，验证持续调整闭环。已完成的示例保存在 `examples/kimi-acceptance/`；新安装的验收目录位于运行数据目录下的 `acceptance-project/`，与产品源码分开。

推荐有“可用性”“建议强度”“额度状态”三种信息，不应压成一个绿灯。也不应先把大模型推荐能力全部做完，最后才发现实际执行路径拿不到最终结果。

## 形态与技术路线

| 形态                | 适用阶段            | 主要取舍                                                         |
| ------------------- | ------------------- | ---------------------------------------------------------------- |
| 本地服务 + Web      | 推荐用于 MVP        | 容易迭代，直接管理本机 CLI；需要明确服务启动、停止和任务后台存活 |
| Electron Mac 客户端 | 工作流稳定后        | 可复用 Web 界面和 TS 服务；增加窗口、通知、安装包和更新维护      |
| 原生 SwiftUI 客户端 | 需要深度 Mac 体验时 | 界面和平台集成能力好；和现有 TS 桥接层形成两套开发栈             |

已采用：TypeScript 本地服务、React Web、SQLite 状态存储、SSE 进度事件，Kimi 通过双向 stdio ACP 接入。第一版不需要额外的终端 WebSocket。

服务至少拆成发现、模型目录、额度、推荐、编排、执行器六个边界。配置和凭证处理在后端，浏览器只收到必要展示状态。模型研究的在线检索也是独立可替换能力，缓存资料供离线／查询失败时使用。

botmux 可复用的重点是 CLI 桥接和会话机制；Orca 可参考发现、模型目录与额度模块。`workflow-core` 等真正需要任意 DAG、复杂循环或恢复时再评估引入。最初“leader → 实现 → review → 汇总”的状态机可以保持简单，同时保留将来对接它的边界。

开工前置项已明确。其余采用默认实现决策：顺序执行、推荐以均衡策略为默认且可修改、先完成 Kimi 适配；后续按实际使用反馈再扩展并发与其他 agent。Kimi 登录或真实协议能力若阻碍验证，再反馈具体需要用户处理的事项。

## 实施中的协议校正

Kimi 2.1.1 ACP 的 `auto` 对应 CLI Ask When Needed；ACP `yolo` 语义更强，不能直接照搬 CLI 同名参数。领队与审查员采用独立自定义 agent 文件，仅开放 Read/Grep/Glob，并使用 ACP default；没有采用原生 plan/ExitPlanMode 流程，因为它会尝试自己继续实施计划。编码成员关闭 Agent/AgentSwarm 和原生计划切换工具，由 Agenthub 外层调度。

真实 `/usages` 当前包含 `usages` 比例对象（5 小时、月总量、月编码量）和 legacy limits，已兼容并去重。公开能力信息优先读取官方模型池定位，目录仅精确匹配别名。官方当前说明 highspeed 价格较高，因此不能用名称推断其更省额度。

公开验证说明记录在 `docs/testing.md`；真实任务的原始证据保留在本地 `artifacts/live-acceptance.json`，不进入开源仓库。
